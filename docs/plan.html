llama-web 开发计划

一个 Nuxt + Bun 的单体项目，替代「llama-swap + 图片代理 + 配置生成脚本」这一堆拼起来的东西。

要解决的问题

  • 原来一个请求要经过 图片代理 → llama-swap → llama-server 三层，出了问题不知道是哪一层。
  • llama-swap 界面是英文的，而且「同时只能在线 1 个」这类规则是隐含的默认行为，界面和配置里都看不到。
  • 模型扫描目录写死在脚本里，改个参数要改 JSON、重新生成 YAML、再重启。
  • 看不到模型实时日志、加载进度、生成速度，崩溃了也不知道原因。

做成什么样

  • 一个进程：自己启动和管理 llama-server.exe，同时提供 OpenAI 兼容 API 和中文管理界面。
  • 一个主端口 :5001（本机与局域网，完整功能），外加一个只给 Cloudflare 隧道用的 :8080（只开放 /v1/*，强制校验 key）。
  • 手动启动：双击 start.bat，关闭窗口即停止服务并结束所有 llama-server。

不做什么

  • 不支持 vLLM 等其他后端（只留接口）。
  • 不做开机自启、系统托盘、桌面程序。
  • 不做多用户和登录。
  • 不做历史统计图表（只显示实时速度）。

核心行为规则

模型状态机

stopped ──请求/手动启动──▶ loading ──健康检查通过──▶ ready
   ▲                         │ 失败/超时                 │ 需要切换到别的模型
   │                         ▼                           ▼
   │                      failed（等手动重试）        draining（不接新请求，等在途请求结束，超时强杀）
   │                                                     │
   └──────────────────────── unloading ◀─────────────────┘
ready ──进程意外退出──▶ crashed ──下一个请求──▶ loading（最多自动一次，再失败 → failed；手动启动 / 重试后重新计）

请求路由

  1. 从请求体读取 model；形如 名字:方案 时拆成模型 + 方案，否则使用该模型的「当前方案」。没有 model 字段时使用当前正在运行的模型。
  2. 目标（模型 + 方案）正在 ready → 直接转发。
  3. 否则进入切换队列：当前模型进入 draining → unloading → 目标 loading → ready，然后转发。多个等待同一目标的请求共享同一次加载。
  4. 等待期间，如果是流式请求，每 15 秒发送一次 SSE 注释行 : loading 63% 保持连接。
  5. 目标模型没有配置 mmproj，但请求里有图片 → 直接返回 400 和中文说明，不去加载模型。
  6. GET /v1/models 由 llama-web 自己返回：已启用模型的基础名 + 每个 名字:方案。

参数合并

最终参数 = 全局默认 ← 模型设置 ← 当前方案的覆盖 ← 方案的「额外参数」。表单项每一项都有「继承 / 自定义」两种状态。额外参数里出现了表单已经管理的参数（例如 -c、--jinja）时给出警告，以额外参数为准。--host / --port 由 llama-web 分配，不允许用户覆盖。

来源识别

:5001 来的请求 = 本机或局域网，免 key。:8080 来的请求 = 公网：只允许 /v1/*，校验 Authorization: Bearer <key>，转交主服务时附带一个每次启动随机生成的内部头来标记来源，外部无法伪造。其他路径一律 404。

风险与待验证

风险应对
关窗口时子进程是否一定退出Windows 下同一控制台的子进程通常一起收到关闭事件；兜底是启动时按 pids.json 清理。阶段 1 实测，不可靠时考虑 Job Object。
1-1 实测（Bun 1.3.14 / Win11）：Bun 启动的子进程会随 Bun 进程一起退出，即使对 Bun 进程 taskkill /F（不带 /T）也是如此，表现同 kill-on-close Job Object；非 Bun 子进程（ping）同样。主动停止用 taskkill /PID <pid> /T /F 杀树，已验证。读取进程可执行文件路径可用 PowerShell Get-CimInstance Win32_Process（较慢，约数秒，只适合启动时清理）。关闭 start.bat 窗口的场景仍留到 1-6 实测。见 tests/platform/process-tree.test.ts。
1-3 实测（真实 llama-server b10809 + 27B Q4 模型，-c 4096）：经 scheduler → runner 加载约 37 秒，/health 200，对话请求 200；手动停止约 3.6 秒，进程树（含 llama-server 自己的子进程）全部结束、端口释放、pids.json 清空；残留清理能杀掉登记过且路径在运行目录下的真实 llama-server，路径不在运行目录下的保持运行。
1-6 实测（构建产物 + llama.cpp b11146）：关闭 start.bat 窗口（经典控制台，发 WM_CLOSE，等同点 ×）后约 3.8 秒内 cmd、bun、llama-server 全部退出，pids.json 被清空（走了优雅退出），端口释放。对 llama-web 执行 taskkill /F（不带 /T）时 llama-server 随之退出，只留下失效的 pids.json 记录，下次启动时被清掉；手动造一个脱离 llama-web 的 llama-server 并登记后启动 llama-web，日志 residue cleanup: killed 1。结论：不需要 Job Object。
sharp 在 Bun + Windows 下的兼容性阶段 1 第二项先验证；不行则图片处理改为 Node 子进程或换库。
1-1 实测：可用。sharp 0.35 在 bun test 和构建产物（.output，bun 运行）里都能缩放、编码 jpeg、读取 webp/gif。见 tests/platform/sharp.test.ts。
Nitro 在 bun 下流式响应被缓冲阶段 1 验证逐 chunk 到达；必要时 /v1 转发改用 Bun 原生处理。
1-1 实测：不缓冲（createEventStream 与直接返回上游 body 都按 400ms 间隔逐 chunk 到达）。但 Nitro 自带的 bun 入口有三个问题：① 只把路径、头和已读完的 body 交给 localFetch，处理函数拿不到 req.signal，客户端断开时上游不会被取消，createEventStream 的 onClosed 也不会触发；② 拿不到客户端 IP；③ Bun.serve 默认空闲超时 10 秒，长时间没有输出的请求（例如非流式请求等待模型加载）会被断开（实测失败）。
应对（已验证可行，见关键决定 25）：用自定义 Bun 入口（nitro.entry，需用绝对路径）：每个请求 server.timeout(req, 0)；/v1/*、/upstream/* 由 Bun 原生处理（逐 chunk 直通、断开时上游被取消、IP 可得）；其余请求交给 localFetch，并通过入口覆盖写入的内部请求 ID 让处理函数取到 signal 和 IP（SSE 断开可感知、静默 30 秒不断）。nuxt dev 用的是 Node 开发服务器，不走该入口，1-4 需要考虑开发模式。
1-4 落地：入口是 server/entry.ts，只在构建时生效（nuxt.config 的 $production；开发模式下 nitro.entry 也会替换 dev worker 的入口，导致 Bun is not defined）。转发逻辑在 server/core/proxy.ts（标准 Request/Response），开发模式由 server/routes/v1/、server/routes/upstream/ 调用同一套逻辑，断开信号来自 Node 响应的 close 事件。给 Nitro 处理函数传 signal / IP 的内部请求 ID 不做了：2-1 的 GET /api/stream 也在自定义入口里原生处理（core/live.ts 的 handleStream，用 req.signal 感知断开），开发模式走 server/api/stream.get.ts。Bun 1.3.14 的崩溃：在响应流的 cancel 回调里对上游 fetch 的 body 调用 reader.cancel() 会让 Bun 段错误（已用独立脚本复现）；改为只通过 fetch 的 AbortSignal 取消上游，上游同样会被取消。
llama.cpp 参数改名导致启动失败更新后首次加载失败时提示回退；errors.ts 识别「未知参数」。
Release 资产命名变化更新失败只记事件，不影响现有版本使用。
data/secrets.json 明文用户已接受；只靠 .gitignore + pre-commit；需要时可以挪出项目目录。
