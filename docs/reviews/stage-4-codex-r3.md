## 后续审查意见

### CR-023 · 高 · 只改分行凭据的值仍漏报，数字限制还削弱原保护

- **位置**：`scripts/pre-commit:23,27,34–45,59`；项目允许格式 `server/core/cloudflare.ts:54–60`。
- **问题描述**：分行规则只记住上一条新增行，diff 使用 -U0，修改已有赋值的值时，原名称行不会进入上下文，guard 因而失效。同时，新规则额外要求值含数字，将旧版已经拒绝的纯字母疑似凭据放行；项目的 cleanApiToken 并不要求数字。
- **触发场景**：已有分行 cloudflareToken 赋值，把下一行的占位值换成凭据，名称行不变；或在单行凭据字段写入符合项目格式、没有数字的长字符串。
- **证据**：V03 驱动实际 hook：值单独变化的合成 hunk 旧/新都退出 0；纯字母长字面量旧 1、新 0，且该合成值被 cleanApiToken 接受。没有放行标记，没有打印任何值。新增分行测试把整份文件一起加入，遗漏最常见的「修改已有值」路径。没有用真实服务验证是否会发放纯字母值，该外部格式细节**待确认**；只改值的已确认漏报不依赖这个问题。
- **建议修改**：从索引中的文件取得必要上下文，识别被修改的字面量是否属于敏感字段，仍只对本次新增/修改值报错；不要用「必含数字」替代凭据上下文。补已有文件只改值的测试，以及项目允许的无数字格式的扫描边界测试。
- **处理结果**：**已修复**。核实成立：-U0 下只改值时名称行不在 diff 里。hook 现在按 hunk 头跟踪行号，遇到「像值」的新增行时用 `git show :文件` 读取暂存文件的上一行（可以是未改动的上下文）判断是否以凭据名称结尾。数字限制不再作为总规则：**带引号的字面量**（`name: '…'`、`"cfToken": "…"`）30 位以上一律拒绝，不要求数字；只有**不带引号**的值（.env / yaml / shell）才要求含数字。新增测试：已提交文件只改值；纯字母带引号字面量被拒；纯字母不带引号的 env 值放行（已知取舍）。

### CR-024 · 低 · 正常函数名带版本号时仍被当作密钥

- **位置**：`scripts/pre-commit:21–27`；测试 `tests/platform/pre-commit.test.ts:159–170`。
- **问题描述**：要求数字没有区分字面量和代码表达式。长函数/变量名可以合法包含版本号、算法编号等，新增允许测试只覆盖没有数字的名称。
- **触发场景**：提交正常代码 `const tunnelToken = extractTokenFromPastedCloudflaredV2Command(raw)`；该行没有凭据。
- **证据**：V03 实际新 hook 对无 V2 的旧反例退出 0，对加入 V2 的正常函数调用退出 1。说明原具体反例修复，但同一类误报仍在。
- **建议修改**：按语法/上下文区分源码表达式与凭据字面量，给环境变量赋值采用对应规则；补长函数、长变量名包含数字的允许测试，同时保持真正凭据拒绝测试。
- **处理结果**：**已修复（到约定的取舍为止）**。核实成立。不带引号的值现在：以 `const` / `let` / `var` 开头的源码声明一律不当凭据；值后面紧跟 `(`（函数调用）不算；其余仍要求含数字。新增测试：名称含 V2 / Sha256 / 2024 的长函数调用、`const x = 含数字的长标识符`。仍会误报的情况：非声明语句里「赋值给带名称的属性、右边是含数字的长标识符且不带调用」（例如 `obj.tunnelToken = loadFooV3`），需要在该行加 `pre-commit:allow`；这是无法区分标识符和 token 的启发式的固有边界。

### CR-025 · 中 · 端口守卫读取缓存，最终保存的 refresh 仍可绕过它

- **位置**：`server/service/context.ts:299,303`；`server/core/cloudflare.ts:761–762`；读取顺序 `server/core/store.ts:161–164`。
- **问题描述**：localPort 用 getSettings 的缓存。手改尚未被 watcher 读取时，每步守卫仍看到预览端口；但最终 settingsRef.update 会同步 refresh 磁盘，并保留刚读到的新 public.port。保存成功且 Hold 对账后，新端口被应用，任务却已把隧道配置在旧端口。
- **触发场景**：任务已完成远端入口写入，获取 token 期间手改公网端口；100ms 文件监听 debounce 未执行，任务立即进入 save。也可能是保存前已有尚未读取的有效手改。
- **证据**：V05 使用实际 JsonStore/openStore、Hold/writePair 和从当前 context 读取的 onSaved，fake token 响应前写入新端口。任务结果 **done**，applyPublic 捕获到 **8081**，远端 service 仍是 `127.0.0.1:8080`。没有启动真实监听器。新增端口测试只改一个已即时可见的回调变量，无法发现此问题。
- **建议修改**：在保存事务里用新鲜且有效的配置验证确认端口，验证必须发生在第一份写入/托管切换前；远端步骤也需使用新鲜配置检查。发生变化应停止并要求重新预览，保留用户的新设置。补真实存储/缓存/待处理 watcher 的接线回归，不能只测试 localPort 变量。
- **处理结果**：**已修复**。核实成立（V05）。`localPort` 现在先 `settingsRef.refresh()`（读磁盘，读不了就用缓存）再取端口，所以每一步（包括 save）看到的是尚未被 watcher 读取的手改，端口不一致就 `port-changed` 停下，保存事务之前就拦截，保留用户的新设置。新增测试用真实 JsonStore 和磁盘上的手改验证「读取方式」；`context.ts` 里那一行本身仍没有集成测试。

### CR-026 · 中 · 已有快照后 SSE 断线，成功的 HTTP 任务结果被丢弃

- **位置**：`app/composables/useCloudflareSetup.ts:32–35,106–116`；状态保留 `app/composables/useLive.ts:34–38`。
- **问题描述**：takeJob 仅判断是否有过快照，不判断其是否仍新鲜。stream 断开时 useLive 保留旧 state，之后成功的 GET/POST job 全被忽略。apply 还清空 plan，busy 结束，但没有 live 更新可以填回 job，界面可能无任务可继续，或一直显示旧任务。顶栏虽显示实时连接异常，也不能补回操作结果。
- **触发场景**：先收到 cloudflare=null 的初始快照，SSE 随后断开但普通管理请求仍能完成；用户执行 apply，收到 done。失败/重试/清理响应也有同类问题。
- **证据**：V10 用 Vue 响应式环境执行真实 composable，只替换 Nuxt 全局和可控请求：已有快照、connected=false，apply 返回 done 后仍 **job=null、plan=null、busy 为空**。新增测试只覆盖「从未收到快照」，没有覆盖「收到后断线」。本轮未运行浏览器。
- **建议修改**：以服务端任务/状态版本仲裁快照与 HTTP 返回，或在实时连接不可用时明确阻止需要 live 的动作并提供恢复方式。不要只按缓存存在与否忽略结果，也不要直接无版本地恢复全部 HTTP 覆盖；补断线后成功/失败/清理，以及重连快照与延迟响应交错的测试，继续保持 useLive 为统一实时来源。
- **处理结果**：**已修复**。核实成立（V10）。`takeJob` 只在 live 已连接且有快照时忽略 HTTP 结果；流断开时快照已过期，使用 apply / retry / cleanup / dismiss 的返回值，重连后的快照再次成为唯一来源，在途的旧响应被忽略。新增测试：断线后 apply 成功、dismiss；重连后在途响应不覆盖快照。未引入服务端版本号（保持 `useLive` 为统一实时来源）。
