### S8-001 · 高 / major · 解压大小和文件数限制在写盘完成后才生效

- **位置**：`server/core/runtime-add.ts:394`、`server/core/runtime-add.ts:403`、`server/core/runtime-add.ts:408`；相关调用 `server/core/archive.ts:82`。
- **问题描述**：磁盘空间按压缩包大小的 3 倍预检；随后完整执行解压，结束后才用 `measureTree()` 检查 6 GiB / 5000 文件的上限。`archive.ts` 的解压前检查只核对路径和条目类型，不计算展开大小或执行写盘配额。压缩率高的文件或大量小文件可在触发 `too-large` 前写满磁盘、耗尽文件系统资源；120 秒超时也不限制这段时间内写出的字节数。这与 8-1 的大小边界及决定 44 的资源保护原则不符。
- **触发场景**：从本机或第三方 GitHub Release 添加体积很小、展开体积很大的归档。此时压缩体积和剩余空间预检均通过，注册和运行程序之前系统就已承受展开负担。
- **验证证据**：使用真实系统 `tar.exe` 和默认 `extractArchive()`，构造 177 字节的 tar.gz；缩小 `maxTreeBytes` 为 1024 字节，注入可用空间 4096 字节。解压器仍先完整写出了 8192 字节的 `padding.bin`，随后才返回 `too-large`。没有执行 `runVersion`。这是缩小尺度的安全复现，没有制造实际磁盘耗尽。
- **建议修改**：解压前检查累计展开大小与条目数量，并用展开预算检查剩余空间；解压过程中也必须限制实际写出的字节和条目，越界立即终止并等待进程结束再清理，不能只依赖压缩体积或事后扫描。叠加 cudart 时也要按同一累计预算计算。
- **缺失测试**：低压缩体积 / 高展开体积、展开体积超过可用空间、文件数超过配额；断言在超过预算前停止写入，而不只是最终返回 `too-large`。
- **处理结果（2026-10-03）：已修复。** 核实成立：`extractArchive` 只在解压后由 `measureTree` 限额。现在 `server/core/archive.ts` 先按 `tar -tv` 列表累加声明的展开大小与条目数（连同目标目录已有内容，叠加 cudart 时累计），超过 `maxBytes` / `maxEntries` 或大于可用空间就在写盘前拒绝；解压期间每 100 毫秒复核目标目录的实际大小，越界即终止进程树并等待其结束。新增错误码 `extract-too-large`，`runtime-add.ts` 映射为 `too-large` / `disk-space`。测试：`tests/core/platform-foundation.test.ts`（真实 tar：越界不写出文件、空间不足、条目数、叠加累计、预算内正常解压、列表解析）。边界：监视是 100 毫秒轮询，监视间隔内仍可能多写一小段；列表里解析不出大小的条目只靠监视兜底。

### S8-002 · 高 / major · 设备探测期间，处于 loading 的运行库仍可被删除

- **位置**：`server/service/context.ts:324`–`338`，重点是 `:327` 的 await 和 `:338` 的保护登记。
- **问题描述**：`planLaunch()` 已解析并检查可执行文件后，指定 GPU 的启动会等待 `deviceProbe.list(plan.exe)`。`launching` 直到探测结束后才登记，而删除保护只查看 `runner.list()` 和 `launching`。这段时间模型已经是 `loading`，却没有对应的运行库保护。删除可以成功清空引用并移除目录，随后旧启动计划仍交给 runner，导致启动失败，违反决定 35 的「正在启动中的不能删」。
- **触发场景**：模型选择一个可删除的自定义运行库和 `CUDA0`；首次设备探测、刷新探测或探测较慢时，另一请求确认删除该运行库。自动清理也存在类似的保护窗口；本轮直接复现的是手动删除。
- **验证证据**：创建真实 `getContext()` 接线，使用临时假配置、假权重和 PE 文件头；将 `DeviceProbe.list()` 注入为可控等待，将 `runner.start()` 替换为观察型假启动器。模型进入 `loading` 后，`runtimes.plan('custom:r1').blocked` 为 `null`，确认删除成功；释放探测后假启动器观察到 `existsSync(spec.exe) === false`，scheduler 转为 `failed`。没有执行真实 llama-server。
- **建议修改**：同步解析计划后、第一次 await 之前就登记本次启动使用的运行库，并用覆盖整个探测和启动过程的 `try/finally` 释放保护；确保设备缺失、探测失败、取消和日志初始化失败也释放。读取设备列表的管理请求也应考虑探测进程与删除的互斥。
- **缺失测试**：真实 context 接线下暂停设备探测，同时发起删除 / 清理，断言版本受保护；再验证失败和取消后保护会解除。现有删除测试直接构造 `usedExes`，没有覆盖登记时点。
- **处理结果（2026-10-03）：已修复。** 核实成立：`planLaunch` 之后到 `runner.start` 之前有 `await deviceProbe.list()`，`launching` 晚于它登记。现在 `server/service/context.ts` 在 `planLaunch` 返回后、第一个 await 之前登记保护，整个探测和启动包在 `try/finally` 里释放（设备缺失、探测失败、启动失败都会释放）。测试：`tests/service/launch-protection.test.ts`，走真实 `getContext()` 接线，探测暂停时断言 `plan().blocked` 非空且 `remove` 抛错、目录还在；启动失败和 `device-missing` 之后保护解除。已确认没有这次修复时该测试失败。仅 Windows 运行（自定义运行库夹具是 `.exe`）。未处理的一点：`GET /api/devices` 的探测进程与删除之间没有互斥（探测只读设备列表、很短，且删除先改名目录，占用时会得到 `locked`）。

### S8-003 · 高 / major · 删除后续写入失败，只恢复目录，没有恢复已清空的模型引用

- **位置**：`server/core/runtime-manager.ts:193`–`204`。
- **问题描述**：删除依次改名目录、保存清空后的 `models.json`、删除运行库登记或修改当前版本。后两步失败时，catch 只把目录改回原名；已经保存的模型 / 方案引用不会恢复。接口返回删除失败，但下一次启动却改为跟随全局，用户原来的版本选择已经丢失。同步执行避免了请求交错，却不能让多个文件写入成为一个事务。
- **触发场景**：删除被模型引用的自定义版本，模型保存成功后 `runtimes.json` 写入失败；或删除既被模型引用又是当前版本的旧官方版本，模型保存成功后 settings 写入失败。
- **验证证据**：使用真实 `JsonStore` 保存临时 `models.json`，在 `registry.remove()` 注入写入失败。结果为 `error: 'failed'`、目录恢复、登记仍存在，但磁盘上的 `savedModelRuntime` 已变成 `null`。现有「配置写入失败恢复目录」测试让第一步模型写入直接失败，漏掉后续失败条件。
- **建议修改**：对模型、登记、settings 和目录维护可恢复的整体删除操作，保留原状态并在任何后续失败时恢复所有已提交步骤；若不能可靠补偿，用持久化操作记录在重启时完成或回滚，并隔离中间状态的通知。补偿失败不能把仍需恢复的目录直接视作普通垃圾删除。
- **缺失测试**：在每个后续写入点分别注入失败，核对目录、磁盘配置、内存配置和实时状态均保持一致；包括补偿写入或改名失败后的重启恢复。
- **处理结果（2026-10-03）：已修复。** 核实成立。`server/core/runtime-manager.ts` 的 `remove` 现在记录已清空的模型 / 方案引用和被移除的登记条目，后续任何一步失败都依次还原登记、模型引用、目录；还原失败的项目写进错误详情（`could not restore: …`）。目录还原失败时仍留在 `.del-` 名下（启动时清理），此时登记和模型引用已恢复，运行库因文件缺失走同通道兜底，不会丢用户选择。测试：`tests/core/runtime-manager.test.ts` 新增「登记写入失败」「settings 写入失败」两种后续失败。边界：没有做跨重启的持久化操作记录；进程在三次写入之间被杀时仍可能留下中间状态（概率很小，未处理）。

### S8-004 · 高 / major · 缺失的自定义运行库按全局通道兜底，忽略登记中的类型

- **位置**：`server/core/runtimes.ts:293`–`294`、`:306`–`310`。
- **问题描述**：fallback 只从官方引用中取通道；任何自定义引用都使用 `host.acceleration`，即全局通道。自定义条目仍在登记中、可执行文件缺失时，`e.accel` 是已知信息，却被丢弃。全局为 CUDA、方案选了 CPU 自定义库时，会兜底到 CUDA 并合并 GPU 默认参数；反向也会静默切成 CPU。这违反决定 35 的同通道兜底和决定 36 的参数语义。
- **触发场景**：自定义 CPU 条目的文件被手动移走或恢复备份时没有恢复二进制，登记和模型引用仍在；本机同时装有官方 CPU / CUDA 版本，全局选择 CUDA。
- **验证证据**：直接调用实际 `resolveRuntimeRef()`，构造 `custom:r1` 为本机 CPU 条目、文件不存在，已安装 CPU `b200` 和 CUDA `b300`。返回 `ref: 'cuda:b300'`、fallback `to: 'cuda:b300'`，而非 `cpu:b200`。若只安装了 CPU 官方版本，错误地检查 CUDA 通道还会报 `no-official`。
- **建议修改**：能找到自定义登记时，以该条目的、本机支持的加速类型确定兜底通道；仅在登记也不存在、类型确实未知时采用明确的缺省策略。另平台条目仍必须遵守本机可用通道约束。
- **缺失测试**：全局 CUDA + 缺失 CPU 自定义文件，以及反向组合；同通道官方版存在 / 不存在两种情况；断言实际运行库、默认参数和事件中的替代版本一致。
- **处理结果（2026-10-03）：已修复。** 核实成立。`server/core/runtimes.ts` 的 `resolveRuntimeRef` 现在对登记里的自定义条目用条目的 `accel` 当兜底通道（该通道在本机可用时），官方引用仍用自己的通道，条目不存在才用全局通道。测试：`tests/core/runtimes.test.ts`（全局 CUDA + 缺失 CPU 条目 → `cpu:b200`；反向 → `cuda:b300`；该通道没有官方版本 → `RuntimeResolveError`，不会悄悄换通道）。默认参数按最终选中的运行库类型取，随兜底结果一致。

### S8-005 · 中 / major · v5 CPU 用户的自定义默认参数升级后不再生效

- **位置**：`server/core/config.ts:214`–`216`，相关 `defaultsFor()` 位于 `:154`。
- **问题描述**：迁移为原 CPU 安装复制了 `currentCpu`，但始终用内置 `DEFAULT_CPU_DEFAULTS` 创建 `defaultsCpu`。旧 `defaults` 虽然保存在文件中，CPU 启动从此读取另一份新默认，原有上下文、线程数、额外参数等全部失去作用。因此「旧 defaults 字段没变」并不代表旧配置行为保持不变，违反 8-2 的迁移验收。
- **触发场景**：v5 Windows 用户已选择 `acceleration: 'cpu'`，并在全局默认中定制了参数；升级后按同一个当前版本启动同一个方案。
- **验证证据**：执行实际 v5→v6 迁移、`normalizeSettings()` 和 `defaultsFor(..., 'cpu')`。旧 `ctxSize: 4096`、`threads: 8`、`extraArgs: '--jinja --no-warmup'` 变成 `32768`、`null` 和内置额外参数；旧字段仍在 `defaults`，却不再用于本次 CPU 启动。上下文增大还会增加系统内存开销。
- **建议修改**：迁移原 Windows CPU 安装时，以已有有效默认参数初始化 CPU 那份，仅补缺省字段；仍尊重已存在的 `defaultsCpu`。考虑旧 `auto` 安装实际使用 CPU 的情形，避免无意改变启动参数。Mac 继续保持单份默认。
- **缺失测试**：使用带定制参数的 v5 CPU 配置，对比迁移前后实际 `planLaunch()` 参数，而不只检查配置字段和值是否保留。
- **处理结果（2026-10-03）：已修复（范围见下）。** 核实成立：迁移让 `acceleration: 'cpu'` 的用户保留 `currentCpu`，却用内置值创建 `defaultsCpu`，原来作用于 CPU 启动的 `defaults` 不再生效。现在迁移 5→6 对 `acceleration === 'cpu'` 的安装用 `{ ...内置CPU默认, ...旧 defaults }` 初始化 `defaultsCpu`；已存在的 `defaultsCpu` 保持不动，其他安装和 Mac 行为不变。测试：`tests/core/channels.test.ts`（定制参数的 v5 CPU 配置迁移后 `defaultsFor(…, 'cpu')` 与旧值一致；CUDA 用户得到内置 CPU 默认且 GPU 默认不变）。未处理且需要知道：`acceleration: 'auto'` 的 v5 用户，迁移时无法知道本机实际用 CPU 还是 GPU，所以不复制；这与决定 36「其他不改」一致，如需要改成别的做法请告诉我。

### S8-006 · 中 / major · 额外参数已覆盖设备，启动检查仍按表单设备拒绝

- **位置**：`server/service/context.ts:326`–`328`；相关 `server/core/launch.ts:226`、`server/core/args.ts:363`–`369`。
- **问题描述**：参数构建器遵循「额外参数优先」，会移除表单生成的 `--device` 并使用额外参数的值；但 `LaunchPlan.device` 仍是覆盖前的表单值。context 用它做设备存在性检查，使本来可运行的最终命令被错误拒绝，违反核心参数合并规则及决定 39 对额外参数的约定。命令预览的设备字段与最终命令也会出现同样的分歧。
- **触发场景**：旧表单选择 `CUDA7`，用户换运行库 / 换机器后在额外参数中写 `--device CUDA0`；运行库实际只有 `CUDA0`。类似地，用 `--device none` 覆盖失效的 GPU 表单值也会被旧值拦住。
- **验证证据**：实际 `planLaunch()` 返回 `plan.device === 'CUDA7'`，生成的参数只有 `--device CUDA0`；对仅含 `CUDA0` 的真实格式设备列表调用实际 `deviceMissing(plan.device, list)` 返回 `true`。没有启动进程。
- **建议修改**：设备检查与预览使用额外参数合并后的有效设备信息，识别 `--device` / `-dev` / 等号形式及 `none`；多设备额外参数继续按既定规则给警告，不能拿已被覆盖的表单设备作为启动前置条件。
- **缺失测试**：旧设备失效但额外参数指定有效 GPU / CPU 的 context 启动测试；覆盖别名与等号形式，核对最终参数、检查对象、预览一致。
- **处理结果（2026-10-03）：已修复。** 核实成立：`LaunchPlan.device` 与预览的 `device` 是覆盖前的表单值。现在 `buildLaunchArgs` 返回最终命令的有效设备（`extraDevice()`：识别 `--device X` / `-dev X` / `--device=X`，`none` 记为 `cpu`，多设备记为 `auto` 且仍给 `extra-multi-device` 警告；没有额外参数设备则用表单值），`planLaunch` / `previewLaunch` 用它，所以启动前的设备存在性检查与命令预览和实际参数一致。测试：`tests/core/device-launch.test.ts`（各写法、`none`、多设备、无关额外参数时保持表单值、检查对象不再是旧值、预览）。

### S8-007 · 中 / major · cancel 只能删除已完成的预览，无法取消进行中的导入

- **位置**：`server/core/runtime-add.ts:278`–`279`、`:349`、`:362`；接口 `server/api/llamacpp/add/cancel.post.ts:6`。
- **问题描述**：导入进行中只有 `working` 为 true，`stage` 直到复制 / 下载 / 解压 / `--version` 全部结束后才赋值。`cancel()` 只检查并删除 `stage`，没有中断当前操作或使操作结果失效。因此取消接口可以返回 `{ ok: true }`，后台仍继续下载、解压、运行用户所选程序并生成可确认的预览。这与方法声明的「停止正在下载」和取消接口语义不一致，在外部程序信任边界上也无法可靠撤销尚未执行的操作。
- **触发场景**：预览耗时较长，用户在下载或版本探测完成前调用不带 stageId 的取消接口。
- **验证证据**：对实际 `RuntimeInstaller.preview()` 注入可控等待的 `runVersion()`。等待期间调用 `cancel()`，释放等待后预览仍成功返回，且随后 `confirm(stageId)` 能登记条目，得到 `previewCompleted: true`、`confirmAfterCancel: true`、`registered: true`。
- **建议修改**：每次预览使用独立取消控制器和操作编号，取消时中断网络、解压及版本探测，禁止被取消的操作发布 stage；等待相关进程结束后清理。控制器需允许下一次导入正常重试，不能仅永久 abort 安装器实例。
- **缺失测试**：分别在下载、解压、运行 `--version` 时取消，断言操作终止、不再执行下一步、无法确认、无临时文件 / 子进程，并验证取消后的再次导入。
- **处理结果（2026-10-03）：已修复。** 核实成立：`cancel()` 只删除已完成预览的暂存目录。现在每次预览新建独立的 `AbortController`，`cancel()`（不带 stageId）在进行中的导入上中止它：下载与解压（本来就接 signal）、`--version` 探测（`defaultRunVersion` 新增 signal，中止时结束进程树并等它关闭）；各步骤之间与探测返回后都检查中止，被取消的导入不发布预览、清理暂存目录并返回新错误码 `cancelled`（HTTP 409，中文文案「已取消添加。」），之后可以正常再次导入。测试：`tests/core/runtime-add.test.ts`（解压中取消、探测中取消，含探测忽略信号仍返回时不发布，以及取消后再导入）。

## 其他重点核查与限制

- **平台隔离**：添加路径在 `runVersion()` 前按 PE / Mach-O / ELF 内容及架构检查；列表、选择、删除和解析检查本机平台，自定义执行路径从受限 id 推导。现有构造平台测试通过；未确认这次改动能通过正常管理接口直接选择并启动另一平台版本。该结论不涵盖用户主动篡改登记元数据、替换已登记二进制的完整性保障，也不等于 macOS 真机验收。
- **归档路径与摘要**：沿用归档路径 / 链接检查，复制目录检查链接真实目标；GitHub 源地址受限，公布摘要不匹配会拒绝，无摘要的登记需要 `acceptUnverified`。路径检查不解决 S8-001 的资源边界。没有重新执行真实第三方 Release 下载或大规模恶意归档攻击。
- **执行确认的已知边界**：按本阶段已记录的决定，`--version` 在预览阶段执行，`acceptUnverified` 只限制后续登记。8-5 必须在调用 preview 前展示并取得运行外部程序的确认；这一尚未实现的界面不列为本轮缺陷。不能把事后 SHA-256 接受按钮描述成执行前授权。
- **host / port**：参数数组直接交给 spawn，额外参数中的 `--host` / `--port`（含等号形式）由构建器剔除，最终加入服务分配值；8-3 对此有测试且通过。本轮没有确认新增的设备字段能绕过这一限制。
- **迁移的授权变更**：旧默认 CUDA 13.3 改为空值代表自动选择，是计划 / 交接记录中明确的用户决定，不作为「升级行为改变」另行报告。S8-005 是另一条未授权丢失 CPU 参数作用的路径。
- **验证缺口**：未执行真实模型 / GPU 推理、多 GPU、多路 CPU / NUMA、macOS 真机或 macOS runner、桌面安装包、HTTP 管理接口端到端及浏览器验收。8-1 至 8-3 原交接中的真机结果仅作为历史背景，不算本轮执行结果。
