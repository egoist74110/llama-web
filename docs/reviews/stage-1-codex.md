## 确定的问题

### CR-001 · 高 · 冷加载流在背压期间断连，租约无法及时释放

- **位置**：`server/core/proxy.ts:242`、`server/core/proxy.ts:298`、`server/core/proxy.ts:311`。
- **问题**：冷加载路径的断连处理只 abort `gone`，释放租约依赖转发循环进入 `finally`。如果下游停止读取，循环会停在 `writer.ready` 或 `writer.write(value)`；abort 上游 fetch 无法唤醒下游 TransformStream 的写入，因此 `finally` 不执行。与 ready 路径在 `ac.signal` abort 时立即释放租约的实现不一致。
- **触发场景**：请求冷加载模型并返回 SSE，读取心跳后停止 pull；模型加载成功、第一块上游数据进入下游写入等待，此时客户端断开，仅 `req.signal` 通知断连（开发模式已有注释说明存在这种通知方式）。模型继续显示 `inflight=1`。请求其他模型时会白等 drain 超时，原转发任务、写入队列和监听器也可能继续滞留。
- **验证证据**：使用真实 `createProxy`、`Scheduler` 和本机临时替身 HTTP 上游，读一次心跳后停止读取。断连前 `ready/inflight=1`；abort 请求信号后等待 100 ms 仍为 `ready/inflight=1`；显式 cancel 下游 body 后才变为 0。替身服务已关闭。
- **建议修改**：为此路径建立幂等的 finish 操作，客户端/租约 abort 时立即释放租约并使下游挂起写入终止；不能仅依赖循环 finally。保留避免对 Bun fetch reader 调用 cancel 的兼容限制。
- **缺失测试**：现有 signal-only 测试在持续读取时断开，没有稳定覆盖“挂在下游写入上且不再 pull”的时序；补充该场景及 drain 强杀时的背压场景。

### CR-002 · 高 · pids.json 写入失败后遗留已启动但生命周期未登记完整的进程

- **位置**：`server/core/runner.ts:269`，关联 `server/core/runner.ts:287`、`server/core/runner.ts:307`。
- **问题**：`spawn` 成功后，`registry.add()` 在 exit/close 处理器和加载计时器安装之前同步执行，且没有异常保护。写盘失败会使 `Runner.start()` 拒绝，但实际子进程仍活着。Scheduler 没拿到返回的 `proc`，无法在加载失败时停止它；Runner 中的 `exited` 又因未安装处理器而永远不结算。
- **触发场景**：启动时 `data/run/pids.json` 无法写入（磁盘空间不足、目录权限或文件锁等）。模型被标为 failed，子进程仍运行；再次尝试可能叠加进程。关闭应用时 `runner.stopAll()` 等待未结算的 exited，最终只能依赖入口 15 秒强制退出兜底；登记失败还使正常残留清理缺少 PID 记录。
- **验证证据**：注入会抛错的 registry，启动不使用 GPU 的替身进程。`start` 已拒绝，`isAlive(pid)=true`、Runner 仍跟踪 1 个进程；直接结束该替身后，`exited` 仍为 pending，跟踪记录仍为 1。替身已结束，输出管道已关闭。
- **建议修改**：spawn 后立即安装完整的生命周期处理器，再执行登记；登记失败须结束该进程树并等待结算，释放端口与内存记录，然后返回明确的加载错误。不能让已启动进程的所有权丢失。
- **缺失测试**：补充 registry.add 写入失败时的存活检查、ready/exited 结算、端口释放、stopAll 不挂起与无残留断言。

### CR-003 · 高 · 初始下载期间的请求会把模型永久锁在 failed

- **位置**：`server/service/context.ts:114`、`server/service/context.ts:125`，关联 `server/core/launch.ts:54`、`server/core/scheduler.ts:192`。
- **问题**：加载只等待残留清理，没有与后台初始获取 runtime 协调。下载尚未完成时 `planLaunch` 抛 `no-runtime`，调度器把它当作模型加载失败保存。下载完成只更新 `llamacpp.current`，不会解除 failed；以后 acquire 直接拒绝，不再尝试加载。当前阶段仅有 state/import 管理接口和状态页，没有用户可调用的 retry 入口。
- **触发场景**：首次启动、导入模型后，在几百 MB 的初始下载完成前发起对话。即使状态页稍后显示 runtime ready，同一模型仍持续返回 503，直至重启应用。其他加载失败或修正错误配置后同样缺乏手动恢复入口。
- **验证证据**：真实 Scheduler 加注入的 launcher，第一次因 runtime 未安装抛 `LaunchConfigError('no-runtime')`，随后把 runtime 标为已安装再 acquire。结果仍为 `failed/no-runtime`，launcher 总共只调用 1 次。静态核对确认 runtime 完成回调未清除该状态。
- **建议修改**：在进入模型加载状态前处理 runtime 尚未准备好的前置条件，避免把“初始获取进行中”记作持久模型失败；至少提供明确的手动重试路径。若决定让请求等待下载，应同时维护计划中的相关规则，不擅自改变真正加载失败不自动重试的约定。
- **缺失测试**：补充“下载期间请求 → 下载完成 → 同一模型可恢复”的服务接线测试，以及普通 failed 模型的用户手动恢复测试。

### CR-004 · 中 · 异步导入以旧快照覆盖后续配置修改

- **位置**：`server/api/import.post.ts:19`、`server/api/import.post.ts:32`，关联 `server/core/importer.ts:345`、`server/core/importer.ts:356`、`server/core/importer.ts:364`。
- **问题**：导入读取 settings/models 后异步扫描，完成后整份替换两个当前文档。期间没有锁、版本检查或重新合并。每个 JSON 文件的原子写入只能防止半文件，不能防止旧快照覆盖新值。
- **触发场景**：两个客户端同时导入不同目录，均从空模型表开始并分配 `main`，两次都报告成功，最后保存的一次却覆盖前一次导入的目录和模型。另一个现实场景是扫描期间 runtime 下载完成写入 current，导入仍把扫描前的空 current 写回，已安装版本随即无法用于加载。扫描期间用户手改 settings 也会丢失。
- **证据**：上述调用链明确把 await 前的 `ctx.getSettings()/getModels()` 传入导入，扫描完成后 `ctx.updateSettings(() => result.settings)`、`ctx.updateModels(() => result.models)` 返回旧快照派生的整份结果。当前导入测试只验证顺序第二次导入，没有并发接线测试。本项为静态路径确认，未对真实配置执行导入。
- **建议修改**：为配置修改建立一致的并发控制；扫描完成后基于最新文档重新规划、校验目录/模型冲突并合并，或在发现修订变化时明确拒绝并让用户重试。单独给导入加锁仍不足以保护后台 setCurrent 与手工重载。
- **缺失测试**：用受控扫描 barrier 覆盖双导入、扫描中 setCurrent 更新和扫描中外部配置重载，断言已提交的修改不会被覆盖。

### CR-005 · 中 · 导入第二次保存失败时没有恢复第一次保存

- **位置**：`server/api/import.post.ts:32`、`server/api/import.post.ts:34`，关联 `server/core/importer.ts:366`。
- **问题**：模板复制、settings 保存、models 保存是三个独立步骤。models 保存失败只返回 500，已经落盘的 settings 不恢复，已经复制的模板也没有清理或待恢复记录。首次导入时全局启动参数会改变，但模型表仍未导入；API 的失败结果没有说明已发生的部分修改。
- **触发场景**：模板复制和 settings 保存成功后，models.json 因权限、文件锁或磁盘错误不能替换。用户收到失败，却留下新默认值、新目录与无模型引用的模板；后续重试基于部分修改的配置继续处理。
- **证据**：catch 仅创建 saveFailed 错误，没有 rollback/recovery 分支；模板复制发生在返回 result 之前。现有测试覆盖模板复制成功与命名冲突，不覆盖 endpoint 两份保存的中途失败。
- **建议修改**：在写入前完成校验与准备，使用可恢复提交记录或可靠的回滚机制，使两个文档与模板的部分失败可识别、可恢复；只删除此次导入新建且尚无引用的模板，保留原有文件。失败结果应准确说明恢复状态。
- **缺失测试**：注入第二份文档保存失败以及模板复制中途失败，核对两个配置的磁盘/内存状态、旧备份和模板残留。

### CR-006 · 中 · 同毫秒备份按字典序裁剪，可能删除较新的备份

- **位置**：`server/core/store.ts:217`、`server/core/store.ts:220`。
- **问题**：同一毫秒的备份使用 `stamp.json`、`stamp-1.json` 等名称，然后直接字符串 sort。`stamp-1.json` 排在无后缀的 `stamp.json` 前；超过 9 次碰撞时数字后缀也不是数值顺序。裁剪因而把新的备份当成旧的删除，无法兑现保留最近备份的约定。
- **触发场景**：一次操作中快速连续保存配置，或多个同步更新在同毫秒发生。回退时可能找不到真正最近的配置，测试也会随磁盘速度间歇失败。
- **验证证据**：依赖安装前后的两次全量测试均在 `tests/core/store.test.ts:59` 失败，最新备份内容分别为 3、4，而期望为 5。另用临时目录固定 Date 到同一毫秒，保留 3 份、连续保存 1–6，实际保留的旧值为 `[2, 3, 0]`，应保留的最近旧值 5 已丢失。临时目录已删除。
- **建议修改**：按时间戳和数值序号共同排序，把无后缀视作序号 0，或使用固定宽度且单调递增的后缀；命名与裁剪必须共享相同的时间顺序定义。
- **测试建议**：将已有测试改为确定性覆盖同毫秒碰撞，并增加至少 12 次保存以覆盖两位数后缀，而非通过等待规避碰撞。

### CR-007 · 中 · 管理导入接口接受跨来源表单请求，缺少来源边界

- **位置**：`server/api/import.post.ts:9`、`server/api/import.post.ts:29`，关联 `server/entry.ts:26`。
- **问题**：管理接口有意给局域网免 key，但当前接口既不检查 Origin/Fetch Metadata，也不限制 JSON 内容类型。h3 的 readBody 会解析 `application/x-www-form-urlencoded`，表单字段 `path` 可以直接触发真实导入。局域网免 key 不等于应信任用户浏览器中任意网站发起的配置写入。
- **触发场景**：用户访问第三方网页，该页面向可达的本机/局域网 llama-web 地址提交表单，path 指向攻击者知道或猜到的有效旧配置文件。接口默认 dryRun=false，能改变模型目录、默认参数并复制模板。攻击者不需要读取响应即可造成副作用。
- **验证证据**：锁定依赖中的 h3 readBody 实际验证：带 `Origin: https://example.com`、表单内容类型和 `path` 字段的请求被解析为对象并返回 200；与真实接口读取 path 的方式一致。真实接口及入口没有来源校验。仅使用无副作用的 h3 替身处理器验证解析行为，没有修改真实配置。
- **待确认的边界**：尚未在用户的 Windows 浏览器验证本地网络访问限制是否会额外拦截外部页面；因此不能声称任意现代浏览器下均可直接利用。服务端缺少来源限制已确认，应避免依赖浏览器版本或网络权限作为唯一保护。
- **建议修改**：保留计划中的局域网免 key，同时为管理写接口拒绝外部 Origin，校验 Fetch Metadata，并严格限制预期的请求类型。允许适当的无 Origin 本机 API 客户端；不要用宽泛 CORS 作为替代。
- **缺失测试**：同源管理操作正常、跨来源 JSON/表单写入被拒绝、无 Origin 的合法本机客户端按约定可用。

### CR-008 · 中 · maxLoaded 坑位已经对运行行为生效，突破固定 1 的阶段规则

- **位置**：`server/service/context.ts:110`、`server/core/scheduler.ts:174`，关联 `server/core/config.ts:99`。
- **问题**：设置归一化保留 maxLoaded 任意值，context 原样传入调度器；调度器只确保不小于 1。因此用户手改为 2 即能同时加载两个模型，已经实现计划标为坑位的可修改在线上限。计划的关键决定 9、阶段 1 调度任务和坑位表均明确固定为 1。
- **触发场景**：阶段 1 依赖手改 JSON 配置，用户把预留字段设为 2，顺序请求 A/B 时 A 不再卸载，两个模型共同占用显存，可能 OOM。若误写非数字字符串，Math.max 得到 NaN，首个加载还可能卡在空的 Promise.race，无法推进队列。
- **验证证据**：实际 normalizeSettings 接受 maxLoaded=2；真实 Scheduler 接收该值后，依次 acquire 并 release A/B，snapshot 中 ready 数为 2。现有 `online limit > 1` 单测也证明此行为已生效。
- **建议修改**：现阶段在应用配置边界拒绝或归一化非 1 的值，同时校验有限整数；调度器内部可以保留将来复用的能力，但不得让坑位字段提前开放行为。
- **缺失测试**：设置加载与 context 接线测试须覆盖 maxLoaded=2、非数字以及正常值 1，保证运行时仅一个在线模型。

### CR-009 · 低 · 两个纯逻辑测试依赖 Windows 路径语义，导致 macOS 无法完成全量验证

- **位置**：`tests/core/residue.test.ts:10`、`tests/core/residue.test.ts:35`；`tests/core/launch.test.ts:9`、`tests/core/launch.test.ts:32`。
- **问题**：residue 的注入进程表测试用 Windows 字符串，但实际 isInsideDir 默认使用当前宿主的平台路径规则；launch 测试给 Windows exe 名选择传入 platform，却把 `join('X:', 'models')` 当作各平台上的绝对路径，预期结果没有 resolve。
- **触发场景**：在 macOS/Linux 上运行纯模块审查或 CI，即使不执行 Windows 真机测试也产生确定失败。注入测试的失败会和真实 Windows 清理问题混在一起，削弱测试结果的可解释性。
- **验证证据**：补齐依赖后全量测试分别在 residue 第 46 行、launch 第 32 行失败。后者实际解析为宿主工作目录下的绝对路径，预期却为相对的 `X:/models/...`。这两项不能据此判定 Windows 生产行为错误。
- **建议修改**：纯逻辑用宿主平台绝对临时路径；需要验证 Windows 路径语义的地方明确注入 platform/path 实现。只有真实 Windows 进程测试应按平台跳过。
- **测试建议**：在 Windows 与 macOS 各执行一次全量测试，纯逻辑保持一致，平台专用测试明确 skip。

### CR-011 · 低 · 待确认：一次成功响应会重新开放崩溃自动重载额度

- **位置**：`server/core/scheduler.ts:322`、`server/core/scheduler.ts:436`。
- **问题**：实现只在“自动重载后还没有成功服务过请求又崩溃”时锁定 failed；重载后只要出现一次 `release('ok')`，下次崩溃又可自动重载。关键决定 22 与状态机写的是“最多自动一次，再失败需手动重试”，没有定义成功响应会重置额度。
- **触发场景**：模型每次重载能服务一个请求，随后又崩溃，系统可持续自动重载，无法按字面规则停在 failed 等待用户处理。
- **证据**：`autoReloaded && !servedOk` 条件和 `tests/core/scheduler.test.ts:293` 明确实现此语义；1-3 交接已提出待用户确认。规则解释尚未获得仓库文档中的明确确认。
- **建议修改**：先确认额度是按应用运行期、连续失败窗口还是其他边界计算，再同时更新计划与相应测试；不建议在审查阶段擅自改变已有实现。
