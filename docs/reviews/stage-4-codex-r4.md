## 后续审查意见

### CR-027 · 高 · 排除源码声明时放行了原本被拒绝的反引号凭据

- **位置**：`scripts/pre-commit:22–25,29–32,67`；测试边界 `tests/platform/pre-commit.test.ts:188–211`。
- **问题描述**：named_literal 只认识单/双引号；named_bare 遇到 const/let/var 开头直接返回。因此以反引号书写的普通 JavaScript/TypeScript 字符串，会同时绕过字面量检查与裸值检查。这个写法是字符串字面量，不能依据「源码声明不能含裸凭据」排除。
- **触发场景**：新增或修改 const 声明的 apiToken 反引号字符串，或 const 对象内的 apiToken 反引号属性；值长于 30 字符、含数字、符合项目接收字符集，无放行标记，也不带其他已知 key 前缀。
- **证据**：V04 对上述两种场景执行实际旧/新 hook：**基线均退出 1，当前均退出 0**。假值运行时构造，没有输出值或修改真实索引。当前单/双引号拒绝测试和源码调用允许测试均可通过，同时漏掉这个常见字面量格式。无需依赖纯字母真实凭据的外部发行规则。
- **建议修改**：识别无插值的反引号字面量，再只对真正的表达式应用源码排除规则；不要因整行是声明就排除内部凭据属性。补顶层声明、对象属性、含数字/不含数字反引号字面量的拒绝测试，并保留版本号函数/标识符允许测试。
- **处理结果**：**已修复**。核实成立。引号集合加入反引号（`${` 不在凭据字符集内，带插值的模板串不会命中）；声明排除只作用于不带引号的值，声明里的字面量（含对象属性）照常检查。顺带补上同类漏报：名称和值之间的 TypeScript 类型标注（`apiToken: string = '…'`、``cloudflareToken?: string | null = `…` ``）；分行写法里名称行以引号结尾、值行接着写字符串内容时，不要求数字。新增拒绝测试：反引号的顶层声明 / `export const` 对象属性 / `let` / 属性赋值 / 类型标注，各分含数字和纯字母两组；分行反引号、名称行开串、分行类型标注；允许测试保留版本号函数 / 标识符，并加入带插值的模板串。已知取舍不变：不带引号的纯字母值放行；非声明语句「属性 = 含数字长标识符」需 `pre-commit:allow`。

### CR-028 · 中 · 收到较新快照后断线，晚到响应会把任务状态改回去

- **位置**：`app/composables/useCloudflareSetup.ts:34–36`；状态保留 `app/composables/useLive.ts:34–39`；测试 `tests/app/cloudflare-setup.test.ts:71–93`。
- **问题描述**：只检查响应到达那一刻的 connected，无法判断响应与最后快照的先后关系。断线不会使已经收到的 done/null 快照失效为更旧的 running；旧请求一旦晚到，就无条件覆盖它，甚至复活已经清除的任务。
- **触发场景**：GET 已取得 running，但返回延迟；live 先推送 done，或随后推送任务清除；SSE 再断线，最后旧 GET 返回。此时无需新的服务端变化，前端就退回 running，直到后续快照纠正；持续断线时不会自行恢复。
- **证据**：V05 用 Vue 响应式和真实 composable，只替换 Nuxt 全局及可控请求。完成快照后断线：**基线 done、当前 running**；清除快照后断线：**基线 null、当前 running**。新测试覆盖的是先断线再请求，以及响应前重连，漏了这个相反交错。`server/core/live.ts:246–250` 对未变化快照去重，也不能承诺轮询立刻纠正界面。本轮没有运行浏览器。
- **建议修改**：给 job/快照/响应增加可比较的服务端状态版本；或者至少记录请求发起时的快照代次，拒绝覆盖该请求之后已收到的快照，再定义可靠的离线动作策略。补完成和清除快照→断线→旧响应、重连后再断线，以及离线失败/重试/清理结果的断言；继续保持 useLive 为统一实时来源。
- **处理结果**：**已修复（采用服务端版本号）**。核实成立。`CloudflareSetup.view()` 返回 `{ job, rev }`，`rev = { boot, seq }`：同一进程内任务内容每变一次 `seq` 加一（以发给页面的那一刻为准，相同版本号一定是相同内容），`boot` 区分进程。live 快照新增 `cloudflareRev`；`/api/cloudflare` 及 apply / retry / cleanup / dismiss 的响应都返回动作结束那一刻的 `view()`（不是运行的返回值）。前端只保留更新的版本，不再看连接状态：快照→断线→旧响应、清除→断线→旧响应、重连后再断线、离线时 apply / retry / cleanup 结果、失败动作不改状态、服务重启（新进程的快照总被采用；旧进程的晚到响应被拒）都有测试。用旧版 composable 跑新测试，三条交错用例失败。仍以 `useLive` 为唯一实时来源，页面没有新增轮询。

### CR-029 · 低 · 多场景 hook 测试超过默认预算，标准验证命令重复失败

- **位置**：`tests/platform/pre-commit.test.ts:110–129`；本轮增加 shell 调用的规则 `scripts/pre-commit:24–37,48,67–70`。
- **问题描述**：一个 test 内串行执行 7 组真实 Git/sh 操作，仍采用默认 5000ms 超时。当前 Windows 环境中标准 bun test 两次都被此预算判失败，尽管提高预算后所有拒绝断言成立，影响要求的标准验证关口。
- **触发场景**：sh 在 PATH 上，执行仓库规定的默认 `bun test`，而不是跳过 hook 或给整个命令额外放宽超时。
- **证据**：V02 两次同一项分别 **5202.77ms、5265.73ms**，均 reported timed out after 5000ms，整体退出码 1。第二次没有并行 hook 复现。V03 仅补充 `--timeout 30000` 后该项 **5227.26ms**、16 条 hook 测试全部通过。V08 按相同 7 组操作隔离比较：基线 **4517ms**、当前 **4947ms**，各场景均正确拒绝。耗时受机器影响；不将这组测量推断为所有机器必失败或生产 hook 有无限阻塞。
- **建议修改**：把每个场景拆成独立 test，或像相邻的多场景测试一样设置明确的合理预算；必要时减少重复 shell 扫描。重新运行不附加超时参数的 `bun test`，不能只用放宽命令代替标准命令通过。
