## 原问题与接线

启动、重试和首次确认接口返回 `{ ok: true }` 时，后台启动尚未完成。缺运行库会通过 LiveHub 发出带 `no-runtime` 的 `loading → stopped` 活动事件，并将实例从快照中移除。因此只处理 HTTP 异常、或等待实例进入 failed 都不能覆盖用户反馈。

1. `useModelActions` 和 `FirstStartDialog` 在请求前登记启动尝试，请求成功后标记 accepted；HTTP 异常也进入同一通知队列。扫描启用的 HTTP 异常直接进入队列。
2. `useModelStartFeedback` 使用现有 `useLive` 活动事件与快照。按模型、方案和操作时的事件基线匹配；处理 stopped 错误，忽略历史记录，避免重复提示和旧 HTTP 响应覆盖新尝试；成功或主动停止清除跟踪。
3. 布局中的 `ModelStartFailureModal` 安装跟随 watcher 并承载队列，首次确认框卸载不影响通知；Vue 作用域卸载时清理 watcher。
4. `model-start-notice` 将原因映射为现有平台文案、处理建议和入口。无运行库直达 `/settings#s-llama`；参数 / 内存 / 设备等错误打开对应模型与方案的参数页；未知原因连接过滤日志。
5. `settings.vue` 在异步设置卡片出现后处理 hash，并处理同页 hash 变化，保证真正滚动到分区。

## 建议审查重点

- 对照后台启动流程核实 stopped / failed / crashed 事件及时间顺序；检查 ready、重试、旧响应和快照回退的匹配。
- 首次确认成功响应后组件卸载、路由切换、事件重放、多失败排队及关闭动作是否丢失或重复提示。
- 处理入口是否定位正确模型 / 方案 / 参数页；运行库导航是否等待实际卡片渲染，避免只改变 URL。
- 界面文案是否给出可执行的下一步，尤其运行库自动下载默认关闭时；Mac 对应原因是否使用平台适当措辞。
- watcher 生命周期与既有非启动动作的 toast 是否保持正确；新增测试是否验证行为而非仅复制实现。
